ARGUS

A physical, local-first AI assistant that uses a dedicated computer as a hub for reasoning, voice, personal tools, and controlled cloud capabilities.

Overview

ARGUS (Adaptive Reasoning and Guidance Utility System) is a local-first personal AI assistant built as a physical device rather than another desktop chat window. A Lenovo ThinkCentre runs the FastAPI backend, local Ollama model, SQLite data store, voice services, and a dedicated 7-inch 1024×600 interface. The core interaction loop works locally, while cloud models and external services are treated as optional capability layers rather than requirements.

The system is designed as an orchestrator: common requests are handled by deterministic Python logic, open-ended requests fall back to the local model, and consequential external actions are placed behind explicit human approval. I designed the architecture, interface, deployment, voice/model integrations, development workflow, and 3D-printed enclosure, treating the software and physical product as one system.

Highlights

  • Deployed physical kiosk — FastAPI/uvicorn, Xorg, Openbox, and Chromium are managed by systemd and enabled at boot on the ThinkCentre.
  • Local-first reasoning and voice — deterministic command routing, local Ollama llama3.2 fallback, browser push-to-talk transcription, and ElevenLabs TTS with graceful text-only fallback.
  • Safety and integrations — SQLite-backed approvals, Google Tasks/Calendar/Gmail support, optional Gemini routing, local project/command history, and 92 automated tests passing in the verified August 2026 state.

Problem

What needed solving.

Most AI assistants are either cloud chat interfaces or isolated automation tools. They do not provide a persistent physical presence, do not unify personal context and actions in one system, and often require sending every request to a remote model. For a device that can eventually manage projects, files, communication, automations, and software-development tasks, I needed an architecture that remained useful locally, reached cloud services only when they added value, and placed human approval between AI reasoning and consequential external actions.

Solution

How I approached it.

ARGUS uses the ThinkCentre as a dedicated local hub. A single FastAPI backend serves the 1024×600 dashboard, routes predictable commands to small Python handlers, falls back to Ollama for open-ended reasoning, stores local state in SQLite, and exposes voice and integration endpoints. The interface presents ARGUS as a central animated presence whose state changes through idle, listening, thinking, speaking, executing, success, error, and approval modes. Google writes and cloud escalation use an approval queue; optional Gemini routing is implemented, while premium Claude/OpenAI execution and broader personal-data connectors remain future work.

System Design

How it fits together.

Physical Interface

Dedicated 7-inch 1024×600 display in a custom 3D-printed enclosure built around the ThinkCentre and audio hardware. Chromium runs as a kiosk, and the central hub state machine gives ARGUS a persistent visual presence.

Local Core

FastAPI/uvicorn backend, deterministic command router, Ollama llama3.2, SQLite database, project/note memory, approval queue, voice transcription, TTS endpoints, and system services. This is the default path and is designed to keep working when optional integrations are unavailable.

Integrations + Cloud

Current optional capabilities include Google Tasks/Calendar/Gmail and Gemini cloud routing behind configuration and approvals. Planned expansion includes premium models, network files and personal context, automations, remote access, and a review-first developer-agent workflow.

Build Process

How it came together.

Step 01

Defined the product architecture: a dedicated physical hub with local reasoning by default, optional cloud escalation, and explicit approval before external side effects.

Step 02

Designed and iterated the 3D-printed enclosure around the 7-inch display, ThinkCentre, speaker, and assembly constraints, refining tolerances, print orientation, and part connections.

Step 03

Built the FastAPI backend and the fixed 1024×600 dashboard, then deployed the physical interface as an Ubuntu kiosk using Xorg, Openbox, Chromium, and systemd services.

Step 04

Added deterministic command routing, local Ollama inference, browser/device voice input, faster-whisper/whisper transcription, ElevenLabs TTS, and SQLite-backed local state.

Step 05

Added Google authentication/integrations, approval-gated external actions, API-budget/model-routing logic, and an optional Gemini fallback; expanded automated coverage to 92 passing tests.

Step 06

Removed superseded legacy code, synchronized the deployed ThinkCentre with GitHub, and created living architecture/current-state/roadmap documentation plus a review-first development workflow.

What I Learned

What I'd carry forward.

ARGUS reinforced that product engineering is a system problem, not a collection of isolated software and CAD tasks. On the hardware side, I learned that enclosure geometry has to be designed around manufacturing realities — print orientation, support material, clearances, assembly access, cables, and real hardware — rather than only the ideal CAD shape. On the software side, I learned to separate deterministic behavior from LLM reasoning, make optional integrations degrade cleanly, and use approval gates, tests, and living documentation to keep an AI-driven system understandable as it grows. The most valuable lesson has been designing the hardware, interface, deployment, and AI architecture together instead of treating them as independent layers.

Next Steps

Where it goes next.

Immediate work is to finish UI polish with self-hosted fonts, replace placeholder CPU/TEMP/MEM/LAN values with live ThinkCentre metrics, and verify the Gemini fallback against a real API key. The next capability layer is broader personal context: network files, project documentation, and additional services that ARGUS can read and act on through controlled tools. Voice will move toward a more natural wake/sleep interaction instead of chunked push-to-talk. The major long-term milestone is a review-first developer-agent loop: receive a feature request, delegate implementation to a coding agent on a development branch, run tests, prepare a commit/PR, and present the change for human approval before deployment.
