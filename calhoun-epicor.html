SolidWorks-to-Epicor Middleware

A Python desktop middleware that automates the transfer of engineering data from SolidWorks assemblies into Epicor — controlled, reviewable, and verified.

Overview

Independently designed and developed a Python desktop middleware application that automates the transfer of engineering information from SolidWorks assemblies into Epicor.

The previous process required users to manually inspect assembly information and recreate the corresponding parts, revisions, bills of materials, and manufacturing operations in Epicor. The application reads the SolidWorks assembly, organizes the required engineering data, checks what already exists in Epicor, and prepares the required creation or update actions.

The system was designed to make ERP automation controlled and reviewable. It includes dry-run functionality, validation, dependency checks, error handling, and post-write verification, so users can review proposed changes before modifying production engineering data. It is deployed in a working state and in final refinement ahead of full production use.

Highlights

Problem

What needed solving.

Engineering data already existed within SolidWorks assemblies, but transferring that information into Epicor required substantial manual review and data entry. Users had to identify required parts, verify revisions, recreate bills of materials and manufacturing operations, and ensure that dependent records existed in the correct order.

This process was repetitive, time-consuming, and vulnerable to inconsistent data entry. Automating it also introduced risk, because incomplete or incorrectly ordered writes could affect important manufacturing information in Epicor.

Solution

How I approached it.

I developed a middleware layer between SolidWorks and Epicor that extracted and organized assembly information, compared it against existing Epicor records, and generated a controlled plan of the required actions.

Rather than immediately writing every detected change, the application let users review the proposed operations through a desktop interface. Dry-run functionality, dependency validation, and post-write verification were incorporated to reduce the risk associated with automating ERP modifications.

System Workflow

How it runs, end to end.

  1. The user selects or opens a SolidWorks assembly.
  2. The application extracts the required assembly and engineering information.
  3. The data is normalized into an internal structure.
  4. Existing Epicor parts, revisions, BOMs, and manufacturing operations are identified.
  5. The application determines which actions are required.
  6. Dependencies and validation conditions are checked.
  7. The user reviews a summary or performs a dry run.
  8. Approved actions are sent to Epicor in the required sequence.
  9. The application verifies the resulting Epicor records.
  10. Errors and results are recorded for review.

Key Engineering Lessons

What I'd carry forward.

This project reinforced that automation involving production engineering data requires more than successful API communication. The application had to account for dependency order, incomplete source data, existing Epicor records, validation failures, and partial-write conditions.

I learned to treat dry runs, verification, and failure handling as core system features rather than secondary improvements. I also gained experience translating manufacturing and engineering processes into structured software while working across CAD, ERP, and production-system boundaries.
